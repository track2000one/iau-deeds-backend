## التغييرات المحفوظة في Railway
أُنشئت خدمات جديدة ووُصلت بمستودعات GitHub على فروع العمل فقط. جميع تغييرات Railway في حالة `STAGED`، أي أنها لا تُشغّل التطبيق ولا تعدّل Production ولا تستنزف خدمات تشغيلية ما لم تُعتمد.

الخادم يستخدم الأمر `npm run start:staging`، ويبدأ برفض أي تكوين لا يتطابق مع:
- معرّف المشروع وبيئة الاختبار المحددين أعلاه.
- `IAU_STAGING_MODE=synthetic-only`.
- قاعدة بيانات محلية داخل الشبكة الخاصة: `postgres.railway.internal:5432/railway`.
- اسم خدمة الخلفية `iau-deeds-backend-staging`.
- منع متغيرات البريد وGoogle Drive وOpenAI والإتصال العام بقاعدة بيانات.

**مهم:** يبدأ مسار الاختبار باستخدام `prisma db push` على قاعدة staging المعزولة فقط **دون** `--accept-data-loss`؛ يمنع أمر Prisma التنفيذ إذا وجد تغييرات تتطلب فقد بيانات. يبدأ بعدها الخادم ومسؤول اختبار واحد دون وظائف الإنتاج الدورية من `src/server.js`.

## ما ينقص قبل التشغيل (إعدادات إلزامية)

1. داخل خدمة الخادم في بيئة staging فقط، إضافة قيمتين سريتين جديدتين في Railway Variables:
   - `JWT_SECRET`: سر عشوائي مستقل عن الإنتاج، طوله 32 محرفًا على الأقل.
   - `BOOTSTRAP_ADMIN_PASSWORD`: كلمة مرور فريدة لمسؤول الاختبار، 16 محرفًا على الأقل.
   **لا تنسخ أسرار الإنتاج ولا تضع هذه القيم في GitHub أو المحادثة.**
2. البريد التجريبي المعين مسبقًا هو `qa-admin@iau-staging.invalid`، وهو عنوان غير قابل للتسليم؛ لا تعيّن بريدًا حقيقيًا له.
3. بعد موافقة المستخدم على نشر **بيئة staging فقط**، تُعتمد تغييرات Railway المجهزة، ويُنشأ عنوان تجريبي للخادم والواجهة.
4. تحديث متغيرات `VITE_API_URL` في الواجهة وعناوين `FRONTEND_URL` و`CORS_ORIGINS` في الخادم بالقيم الصحيحة الخاصة بـ staging فقط، ثم إعادة بناء الواجهة.
5. لا تُستخدم أي نسخة من قاعدة الإنتاج، ولا تُرفع مرفقات أو صور أو هويات أو سجلات حقيقية إلى بيئة الاختبار.

## سيناريو القبول
- فحص `/api/health` بعد تشغيل الخادم.
- تسجيل الدخول بحساب المسؤول التجريبي والتحقق من فتح `/#/reports/executive`.
- إنشاء بيانات اصطناعية للمباني والصكوك والأراضي والمعاينات والمعاملات، ثم مطابقة الأرقام مع التقرير.
- اختبار موظف مصرح له بمشاهدة السجل المركزي فقط، ومنع وصوله إلى باقي الوحدات وملفات التصدير بحسب الصلاحيات.
- اختبار حساب دون `reports.canView`، والتأكد من منع فتح صفحة التقرير.
- تصفية حسب الحرم والفترة الزمنية، وتصدير `Executive_Summary` و`PowerBI_Data` و`Campus_Distribution`.
- معاينة PDF باتجاه RTL وتدقيق ظهور الخطوط والملاحظات والإحداثيات.
- فحص فشل تحميل مصدر منفرد دون عرضه على أنه صفر.
- بعد نجاح الاختبار المصرح به يمكن رفع توصية بدمج PRs ونشر تحديث الواجهة في الإنتاج **بموافقة منفصلة**.

## موانع الإطلاق
- لا تفتح قاعدة PostgreSQL التجريبية إلى الإنترنت عبر TCP Proxy.
- لا تفعّل صلاحيات بريد أو Drive أو OpenAI في الخادم التجريبي.
- لا تستخدم `DATABASE_URL` الخاصة بالإنتاج أو بيئة `iau-deeds-restore-test`.
- لا تعتمد تغييرات staging قبل اكتمال المتغيرات السرية وتثبيت المصادر.
- لا تستخدم `npm start` في بيئة staging؛ استخدم `npm run start:staging` فقط.

## الموقف الحالي
**مجهز للمراجعة، غير منشور.** يلزم تهيئة السرّين، وتثبيت العناوين التجريبية بعد النشر الموافق عليه، ثم إجراء اختبار قبول متصل. لا يوجد حتى الآن ربط مباشر مع Power BI.
